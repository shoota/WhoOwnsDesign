# デザインシステムの基礎とコア価値

## 概要

本文書は、WhoOwnsDesignリポジトリの文書設計の根拠を固めるために行った調査ログである。「AIを使ってデザインシステムによるWebアプリケーションを構築するときに、AIやチームに何を・どの粒度で・どの形式で用意すべきか」という問いを念頭に置き、デザインシステムの基礎概念から近年の潮流までを横断的に調査した。

---

## 1. デザインシステムの定義

### 1.1 主要な定義の比較

| 出典 | 定義 |
|------|------|
| **Nielsen Norman Group (NN/G)** | "A complete set of standards intended to manage design at scale using reusable components and patterns." ——スケールでデザインを管理するための、再利用可能なコンポーネントとパターンを用いた完全な標準セット |
| **Figma Blog** | "A set of components and standards that help keep a product or experience consistent in its look and feel." ——製品・体験の外観と感触を一貫させるための構成要素と標準のセット |
| **Frontify** | デザイナーと開発者が一貫したユーザー体験を生み出すための各種リソースを含むツールキット |
| **Brad Frost (Atomic Design)** | ページではなくシステムとして設計するための方法論。再利用可能なパターンと共有語彙により、スケーラブルで一貫したインターフェースを構築する |
| **NN/G (style-guide定義との対比)** | "A living, complete set of standards intended to manage design at scale using reusable components and patterns" ——「生きている」という点がスタイルガイドとの決定的な違い |

**共通するキーワード**: スケール、再利用性、一貫性、標準、生きているシステム（Living System）

### 1.2 デザインシステムの本質的な特徴

- **単なる成果物の集合ではなく、プロセスと文化を含む**: システムは文書やコンポーネントの集合に留まらず、意思決定プロセス、ガバナンス、組織文化を包含する
- **プロダクトとして運用される**: 使われ、メンテナンスされ、進化するプロダクトとして扱われる
- **人間とマシンの両方が消費する**: 近年はAIエージェントもデザインシステムの消費者となっている

## 2. デザインシステムと関連概念の違い

### 2.1 用語の整理

下図は「同心円モデル」で整理できる。外側に行くほど包括的。

```
┌─────────────────────────────────────┐
│           デザインシステム            │
│  ┌─────────────────────────────┐    │
│  │       パターンライブラリ      │    │
│  │  ┌───────────────────────┐  │    │
│  │  │   コンポーネントライブラリ │  │    │
│  │  │  ┌─────────────────┐  │  │    │
│  │  │  │   スタイルガイド  │  │  │    │
│  │  │  └─────────────────┘  │  │    │
│  │  └───────────────────────┘  │    │
│  └─────────────────────────────┘    │
│  + 原則・ガバナンス・ツール・トークン   │
└─────────────────────────────────────┘
```

### 2.2 各概念の定義と違い

| 概念 | 定義 | 含むもの | 含まないもの |
|------|------|----------|-------------|
| **スタイルガイド (Style Guide)** | ビジュアル一貫性を確保する焦点を絞ったドキュメント。3種類: コンテンツスタイルガイド（トーン・文法）、ブランドスタイルガイド（色・タイポ・ロゴ）、フロントエンドスタイルガイド（レイアウト・UIコンポーネント・コードスニペット） | 色、フォント、画像ガイドライン、コンテンツルール | インタラクションパターン、コード実装、ガバナンス |
| **UIキット (UI Kit)** | Figmaなどで配布されるデザイン素材集。コンポーネントのビジュアル定義のみ | Figmaコンポーネント、カラーパレット | コード、ドキュメント、原則、ガバナンス |
| **コンポーネントライブラリ (Component Library)** | 再利用可能なコード化されたUI要素の集合。ボタン、入力フィールド、モーダルなど個別要素 | コードコンポーネント、プロパティ仕様 | パターン、ブランドガイドライン、ガバナンス |
| **パターンライブラリ (Pattern Library)** | 複数のコンポーネントが組み合わさって解決する再利用可能なUXソリューション集。認証フロー、検索フィルタリング、データテーブルなど | コンポーネントの組み合わせ方、ユースケース | ブランド原則、コードベース |
| **デザインシステム (Design System)** | 上記すべてを包含し、さらに原則・ガバナンス・貢献ガイドライン・ツール・トークンを加えた包括的な枠組み | すべて + 原則・ガバナンス・貢献プロセス | — |

### 2.3 NN/Gによる補足

NN/Gは「デザインシステムとスタイルガイドは親子関係」と明確に定義している。デザインシステムが親であり、スタイルガイドはその子要素。決定的な違いは「スケールでの管理」と「生きているシステム（継続的更新）」という側面である。

## 3. デザインシステムの構成要素

### 3.1 構成要素の分類モデル比較

複数の論者・組織がそれぞれの分類モデルを提唱している。

#### NN/G モデル（2つの大分類）
1. **リポジトリ**: スタイルガイド、コンポーネントライブラリ、パターンライブラリ
2. **管理チーム**: インタラクションデザイナー、ビジュアルデザイナー、開発者

#### Figma モデル（3階層）
1. **デザインシステム全体**: 技術仕様、デザイントークン、ドキュメント、ベストプラクティス
2. **コンポーネント・パターンライブラリ**: 再利用可能なビジュアル要素とインタラクションパターン
3. **基本要素**: 色、タイポグラフィ、アイコン、ロゴ

#### UXPin モデル（4要素）
1. デザイン原則（企業の設計哲学）
2. スタイルガイド（ブランド・ビジュアルルール）
3. コンポーネントライブラリ（コード化されたUI要素）
4. ガイドライン（使用方法と時期）

#### 現代的な拡張モデル（トークンファースト時代）

```
デザインシステム
├── 1. 原則 (Principles)           ← 意思決定の根拠
├── 2. トークン (Tokens)            ← すべての源泉（Source of Truth）
│   ├── プリミティブトークン         ← 生の値（#0057FF, 16px）
│   ├── セマンティックトークン        ← 用途別参照（color-action-primary）
│   └── コンポーネントトークン        ← 特定UI向け（button-background）
├── 3. コンポーネント (Components)   ← トークンからの派生物
├── 4. パターン (Patterns)          ← コンポーネントの組み合わせ
├── 5. ガイドライン (Guidelines)    ← 使用方法・アクセシビリティ
├── 6. ドキュメント (Documentation) ← 意図・根拠・例示
├── 7. ツール (Tools)               ← Storybook, Figma, Style Dictionary等
└── 8. ガバナンス (Governance)      ← 更新・貢献・意思決定プロセス
```

### 3.2 構成要素の性質比較

| 構成要素 | 主な消費者 | 形式 | 更新頻度 |
|----------|-----------|------|----------|
| 原則 | 全員（人間・AI） | 文章・リスト | 低（方向性変化時） |
| トークン | デザイナー・開発者・AI | JSON/YAML/CSS変数 | 中（テーマ追加・改訂時） |
| コンポーネント | 開発者・AI | コード＋Figma | 高（機能追加・修正）|
| パターン | デザイナー・プロダクト | ドキュメント＋例示 | 低〜中 |
| ガイドライン | デザイナー・コンテンツ | 文章 | 中 |
| ドキュメント | 全員 | Markdown・Storybook | 高（変更に追随）|

## 4. なぜデザインシステムを作るのか

### 4.1 解決する課題

デザインシステムが生まれる背景には、以下の痛みがある。

- **視覚的不一貫性**: チームや時期によってボタンの色やスタイルがバラバラ
- **重複作業**: 同じUIを複数のチームが独立して再発明する
- **デザイン-開発間のギャップ**: FigmaとコードのUIが異なる状態が常態化
- **スケールの困難**: チームや製品が増えると品質維持が指数的に困難になる
- **オンボーディングコスト**: 新メンバーがどのUIをどう使うべきか学ぶのに時間がかかる
- **アクセシビリティの後退**: 個別実装では毎回アクセシビリティ対応を忘れやすい

Brad Frostは指摘する: 「プロジェクトの難易度はページ数ではなく、含まれる機能とコンポーネントで判断すべき」。ページメタファから脱却し、システム思考に移行する必要がある。

### 4.2 提供価値（ビジネス・開発・デザインのROI）

#### 定量的エビデンス（Sparkbox Research）

Sparkboxが行ったIBM Carbon Design Systemを用いた実証研究によれば（対象: 社内開発者8名、タスク: コンタクトフォームをスクラッチおよびCarbonで実装）:

- フォームページの開発速度が **中央値で47%高速化**（手コーディング: 中央値4.2時間 → Carbon使用: 中央値2時間）
- 個人差があり、削減幅は参加者によって **27%〜55%** にわたる（全参加者でCarbonの方が速かった）
- ビジュアル一貫性においても、デザインシステム使用上位2名が手コーディング組を上回った
- アクセシビリティについては結果が混在（2名は手コーディング版がCarbon版を上回り、Sparkboxの高い既存アクセシビリティ水準が影響したと研究者は考察）

#### 広範なROI指標

- **671%のROI**: Forrester の調査を引用した LinkedIn 記事がこの数値を紹介しているが、元の Forrester レポートの詳細や調査方法は公開情報から確認しにくく、数値の出典の信頼性には留保が必要
- **ブランド一貫性の向上**: デザインシステム導入企業でブランド一貫性とユーザー満足度の改善が報告されているが、具体的な定量値は出典によって異なるため注意が必要
- **開発速度の向上**: 共通語彙の確立によるコミュニケーションコスト削減
- **アクセシビリティリスク低減**: WCAG/ADA準拠をシステムに組み込むことで個別対応コストを削減

#### 価値の次元別整理

| 次元 | 価値 | 説明 |
|------|------|------|
| 効率 | 開発速度 中央値47%改善（Sparkbox研究） | コンポーネント再利用による重複作業排除 |
| 品質 | 視覚一貫性・アクセシビリティ向上 | 「正しい実装」が簡単になる |
| 組織 | 共通言語の構築 | 職種間コミュニケーションコスト削減 |
| スケール | 新機能追加コスト低減 | 既存トークン・コンポーネントへの追加 |
| ブランド | アイデンティティの一貫性 | 全タッチポイントでのブランド表現の統一 |
| リスク | アクセシビリティ・セキュリティ対応 | システムレベルでの対応内包 |

## 5. デザインのコア価値

### 5.1 一貫性 (Consistency)

**なぜ重要か**: ユーザーは異なるページや機能間で、同じ操作が同じ結果をもたらすことを期待する。一貫性のない体験は認知負荷を高め、信頼を損なう。

**デザインシステムとの関係**: すべてのコンポーネントが同一のトークンから派生するため、色・スペーシング・タイポグラフィが自動的に統一される。

**トレードオフ**: 一貫性が過度になると柔軟性が失われる。異なるプロダクトや文脈で「同じである必要があること」と「違ってよいこと」を明確に定義することが鍵。

### 5.2 効率性 (Efficiency)

**なぜ重要か**: デザイナーと開発者が毎回ゼロから作らず、確立されたパターンを活用することで、ビジネス価値を生む機能開発に集中できる。

**デザインシステムとの関係**: Sparkboxの研究が示すように、デザインシステムの使用で開発時間が半減する。設計判断の再実行コストが下がることで、イテレーションが加速する。

**トレードオフ**: 効率化のために汎用コンポーネントを増やすと、特定用途に最適化されたソリューションよりも複雑になりうる。「スノーフレーク（単一用途コンポーネント）」をシステムに取り込むべきでないというBrad Frostの立場はこのトレードオフを意識したもの。

### 5.3 スケーラビリティ (Scalability)

**なぜ重要か**: チーム・製品・プラットフォームが増加しても、品質を維持できること。デザインシステムがなければ、スケールは品質低下と同義になりやすい。

**デザインシステムとの関係**: トークン階層（プリミティブ→セマンティック→コンポーネント）により、テーマ変更やブランド変更が局所的修正で全体に波及する。

**トレードオフ**: スケーラビリティのための抽象化は学習コストを増やす。設定項目が多すぎると、実装チームがシステムを「難しい」と感じ回避する。

### 5.4 アクセシビリティ (Accessibility)

**なぜ重要か**: WCAG等の基準への準拠は法的・倫理的責任であるとともに、より多くのユーザーに価値を届ける手段。個別実装で毎回対応すると漏れが生じやすい。

**デザインシステムとの関係**: コンポーネントレベルでのアクセシビリティ対応（コントラスト比、ARIA属性、キーボード操作）を内包することで、利用者は「正しいコンポーネントを使うだけで自動的に準拠」できる状態を実現できる。

**トレードオフ**: アクセシビリティ基準を過度に厳格に適用すると、デザインの自由度が下がる。「最低限の保証」と「望ましい実装」のレベルを明確化することが重要。

### 5.5 ブランド整合性 (Brand Coherence)

**なぜ重要か**: ユーザーが複数の接点でブランドを体験するとき、一貫したアイデンティティが信頼と記憶を生む。

**デザインシステムとの関係**: ブランドの意思決定（色、フォント、ボイス）をトークンに集約することで、全プラットフォームへの変更が単一箇所からの修正で実現する。

### 5.6 意思決定の高速化 (Decision Velocity)

**なぜ重要か**: デザイナーや開発者が毎回「ボタンの色は何を使うべきか」を悩む必要をなくすことで、より高次の問題に集中できる。

**デザインシステムとの関係**: 「決まっていることを決まっているとする」ための仕組みがデザインシステム。設計原則とトークンが意思決定の基準となり、個人の判断に依存しない一貫性が生まれる。

DEPT®エージェンシーは指摘する: 「デザインシステムの最も重要なアウトプットは、しばしばデザインそのものではなく、デザインインテントを橋渡しすること」。

## 6. デザインシステムの成熟度モデル

### 6.1 InVision「The New Design Frontier」モデル（5段階）

2019年にInVisionが2,200以上の組織を調査した結果に基づく。

| レベル | 名称 | 特徴 |
|--------|------|------|
| **1** | プロデューサー (Producers) | ピクセルレベルの表層デザインに注力。基本的なビジュアル一貫性を目指すが、プロセス・コラボレーション・技術を見落とす。全体の41%がここ |
| **2** | コネクター (Connectors) | チームを跨ぐ連携が始まるが、散発的 |
| **3** | アーキテクト (Architects) | 紙上では成熟して見える。規模化された効率的なデザインを実施 |
| **4** | サイエンティスト (Scientists) | 開発者・PM・データアナリストとの深いパートナーシップにより、デザインが学習と意思決定ツールになる |
| **5** | ビジョナリー (Visionaries) | デザインテクノロジーで顧客体験とビジネスプロセスの標準を再定義。全体の5%のみ |

### 6.2 Sparkbox 成熟度モデル（4段階）

Ben Callahan氏による実践的な4段階モデル。

| 段階 | 名称 | 主な課題 | 測定指標 |
|------|------|----------|----------|
| **1** | バージョン1の構築 | 最初のリリースへの到達。迅速さと価値のバランス | 初期利用者の定性的価値 |
| **2** | 採用の成長 | 複数チームによる実際の利用 | 採用率、実装バリエーション数 |
| **3** | 十代を乗り越える | 経営層への価値実証。柔軟性と一貫性のバランス | 開発効率、一貫性スコア、アクセシビリティ後退率 |
| **4** | 健全なプロダクトへの進化 | ガバナンスと貢献モデルの確立 | エンゲージメント、オンボーディング速度、プロダクト指標 |

**発生源の違い（段階1）**:
- **グラスルーツ型**: 個人の情熱で駆動、予算なし、小規模グループ → 採用が早期採用者の自発的参加に依存
- **トップダウン型**: 経営層主導、正式予算、委員会による決定 → 使用が義務化されるリスク

### 6.3 UXPin 4段階モデル

| 段階 | 名称 | 特徴 |
|------|------|------|
| **1** | ファウンデーション | 散在したコンポーネント、最低限のドキュメント |
| **2** | スケーリング | 採用の拡大、プロセスの確立 |
| **3** | 成熟 | 広く採用され、ガバナンスが機能 |
| **4** | エボリューション | 継続的な進化、新要求への対応 |

## 7. Single Source of Truth (SSOT)

### 7.1 概念の定義

Single Source of Truth（SSOT）とは、「すべてのデザイントークン、コンポーネント、ガイドラインが保存・管理される一元的なリポジトリ」を指す。

デザインシステムにおけるSSOTの本質: **トークンが意思決定であり、その他はすべてトークンから派生した出力**。

### 7.2 なぜSSOTが難しいか

実際には複数のSSOTが共存するケースが多い:

- **Figma**: ビジュアルコンポーネントのSSOT
- **Storybook**: コードコンポーネントのSSOT
- **Design tokens JSON/YAML**: スタイル値のSSOT

この分散が「デザインとコードの乖離」を生む根本原因。Figmaで更新されたデザインがコードに反映されない、あるいはコードで修正されたコンポーネントがFigmaに反映されないという問題が日常的に発生する。

### 7.3 トークンをSSOTとする現代的アプローチ

近年の成熟したデザインシステムでは、**デザイントークンをSSOTの核心**に置く。

```
[トークンファイル(JSON/YAML)]
         ↓ Style Dictionary等で変換
[CSS変数] [iOS Swift] [Android XML] [Figma Variables]
         ↓
[コンポーネント] ← トークンを参照（直接の値を持たない）
         ↓
[製品実装]
```

Brad Frostの立場: 「コードが真実の源であり、Figmaライブラリはその約束・契約」。FigmaのライブラリはコードのSSOTを反映すべきであり、逆ではない。

### 7.4 W3C Design Tokens Specification（2025.10）

2025年10月、Design Tokens Community Groupは**デザイントークン仕様の最初の安定版（2025.10）**を公開した。これは、ツールやプラットフォームを跨いでデザイン決定を共有するための、プロダクション対応・ベンダー中立のフォーマットを提供する。

主要機能:
- トークンのリッチな関係性（継承、エイリアス、コンポーネントレベル参照）
- プリミティブ・セマンティック・コンポーネントの3層構造の標準化
- JSON形式でのツール間相互運用性

## 8. Atomic Design とその後継思想

### 8.1 Atomic Design（Brad Frost, 2013）

**5つの階層**:
1. **Atoms（原子）**: ボタン、入力フォーム、ラベルなど最小のUI要素
2. **Molecules（分子）**: 原子が組み合わさった機能単位（例：検索フォーム＝ラベル＋入力＋ボタン）
3. **Organisms（有機体）**: 分子が組み合わさったUIセクション（例：ヘッダー）
4. **Templates（テンプレート）**: ページのワイヤーフレーム的構造
5. **Pages（ページ）**: テンプレートに実際のコンテンツが充填された状態

**重要な思想転換**: Atomic Designはページを「設計対象」から「テスト場所」に変えた。設計の対象はシステム（原子→分子→...）であり、ページはその具現化に過ぎない。

**NN/Gの定義との対応**:
- Atoms・Molecules ≒ コンポーネントライブラリ
- Organisms・Templates ≒ パターンライブラリ
- Pages ≒ プロダクト実装

### 8.2 近年の潮流: Subatomic Design / Token-First

Brad Frost自身も近年、Atomic Designの限界を認めている。2024〜2025年にかけて、より深い「亜原子」レベル—すなわち**デザイントークン**—が事実上のシステムの基底となっている。

**トークンの3層アーキテクチャ（現代標準）**:

```
プリミティブトークン (Primitive Tokens)
例: blue-500 = #0057FF, space-4 = 16px
         ↓ 参照
セマンティックトークン (Semantic Tokens)
例: color-action-primary = {blue-500}
    spacing-button-padding = {space-4}
         ↓ 参照
コンポーネントトークン (Component Tokens)
例: button-background = {color-action-primary}
    button-padding = {spacing-button-padding}
         ↓ 実装
コンポーネント
```

**このアーキテクチャの利点**:
- テーマ切り替えはセマンティックトークンの参照先を変えるだけで実現
- ダークモード対応も「同一のセマンティックトークン → 異なるプリミティブ値」で実現
- コンポーネントは「色が何色か」を知らず「どの役割の色か」だけを知る

Supernova の State of Design Tokens 2024 レポートによれば、**回答者の約74%がデザイントークンを採用**していると報告されている（ただし「成熟したデザインシステム」に限定した数値かどうかは元レポートの詳細確認が必要）。

## 9. デザインシステムをプロダクトとして運用する

### 9.1 「Design System as a Product」という考え方

デザインシステムを、内部の利害関係者（デザイナー・開発者・PM）を顧客とする**内部プロダクト**として運用する考え方。

**プロダクト思考の実践**:
- ユーザー（利用チーム）のニーズ調査
- バックログ管理とロードマップ
- バージョニングとリリースノート
- SLA（サービスレベル合意）の設定
- KPI（採用率・コンポーネント利用率・開発速度）の測定

Brad Frostの警告: 「デザインシステムチームが内向きに焦点を当てる傾向がある。実際の仕事は、他のデザイナーと開発者の生活を楽にすること（顧客サービス）」。

### 9.2 チームモデル（Nathan Curtis / EightShapes）

| モデル | 説明 | 長所 | 短所 |
|--------|------|------|------|
| **ソリタリー（孤立型）** | 単一チームが独自に構築して他に提供 | 迅速な意思決定 | 採用チームのニーズを反映しにくい |
| **中央集権型 (Centralized)** | 専任チームがシステムを構築・配布 | 一貫性、プロダクトバイアスなし | 実プロダクトの制約から遊離しやすい |
| **フェデレーテッド型 (Federated)** | 複数プロダクトチームの代表が協働 | 実用性、複数視点 | 意思決定が遅い、誰も所有しない問題 |
| **ハイブリッド型** | 専任コアチーム＋各プロダクトチームの貢献者 | 安定性と現実性の両立 | 調整コスト |

**推奨**: ハイブリッド型が最も多くの組織で機能。コアチームがプリミティブトークンと貢献プロセスを所有し、プロダクトチームがガードレール内で拡張する。

### 9.3 ガバナンスモデル

| モデル | 説明 | 適した組織規模 |
|--------|------|---------------|
| **中央集権型** | コアチームが全決定 | 小〜中規模 |
| **フェデレーテッド型** | 委員会制 | 大規模だが意思決定が滞りやすい |
| **ハイブリッド型** | コアチーム＋貢献ルール | 中〜大規模 |

重要な洞察（DEPT®）: 「ガバナンスモデルの選択よりも、それを支えるリチュアル（会議・プロセス）と意思決定権の設計が重要」。

## 10. よくある失敗パターン・アンチパターン

### 10.1 採用されない（The Adoption Problem）

**症状**: チームが独自のコンポーネントを再発明する、シャドウコンポーネントが増殖する

**原因**:
1. **過度なエンジニアリング**: 実際の需要に基づかずコンポーネントを大量に先行構築 → 複雑すぎて使えない
2. **バイインの欠如**: トップダウンで押しつけられ、現場が「自分たちのものでない」と感じる
3. **ドキュメントの不足**: 「どれを使えばいいか」「なぜこれが存在するか」が伝わらない

**対策**: 採用はステージ別に管理。発見 → 学習 → 使用 → メンテナンス の各フェーズでの離脱ポイントを特定し、フェーズ別に対策を打つ。

### 10.2 メンテされない（The Maintenance Problem）

**症状**: バグが放置される、ドキュメントが陳腐化する、新機能への追随が遅れる

**原因**:
1. **明確な所有権の欠如**: 誰が責任者かが不明確
2. **運用リソースの未確保**: 「作ること」には投資したが「維持すること」への投資がない
3. **更新スキルの不足**: 軽微な変更が全体に意図しない影響を与えることへの恐れ

**対策**: 「デザインシステムは自分自身をメンテできない」という現実を受け入れ、明示的なリソースを割り当てる。

### 10.3 デザインと実装の乖離（The Design-Development Gap）

**症状**: Figmaのデザインと実装のコンポーネントが別物になる、デザイナーが「自分の意図と違う」と指摘し続ける

**原因**:
1. 異なる解釈・タイムライン・優先順位
2. デザインツールとコードの二重管理
3. デザインインテント（意図）が文書化されていない

**対策**: DEPT®の指摘: 「最重要な出力はデザインそのものではなく、デザインインテントの橋渡し」。意図・制約・理由をトークンやコンポーネントのドキュメントに明示的に記録する。

### 10.4 特定チームのサイロ化（The Silo Problem）

**症状**: エンジニアリングが「開発ツール」として、マーケティングが「ブランド管理ツール」として使い、統一的な価値が生まれない

**原因**: 特定の職能チームのニーズに偏った設計・ガバナンス

**対策**: クロスファンクショナルなガバナンス（設計・開発・プロダクトの代表）と、共通KPIの設定。

### 10.5 アンチパターン一覧

| アンチパターン | 問題 | 対策 |
|---------------|------|------|
| 過剰構築（Build-first） | 使われないコンポーネントの山 | 実際の製品ニーズから逆算 |
| 孤島化したオーナーシップ | チーム間で乖離が進む | ハイブリッドガバナンス |
| ドキュメント無視 | 「なぜ」が伝わらない | 意図と根拠の明文化 |
| 一度作って終わり | 陳腐化するシステム | プロダクト思考での継続運用 |
| 完璧主義の先送り | リリースが永遠に来ない | MVP的段階リリース |
| メンテナー不在 | システムの腐敗 | 明確な所有権と工数確保 |

## 11. AIとデザインシステムの新たな関係

### 11.1 AIがデザインシステムを消費する時代

2024〜2025年にかけて、AIコードエージェント（Claude、GitHub Copilot等）がデザインシステムを直接消費する事例が急増している。

**Figma MCP Server（2025年）**: FigmaのデザインデータをAIエージェントが直接参照できるMCPサーバー。デザイントークン、コンポーネント仕様、Code Connect マッピングをAIに提供し、「デザインインフォームドなコード生成」を実現する。

**AIがデザインシステムに期待するもの**:
1. **セマンティックなトークン名**: `blue-5`ではなく`color-feedback-error`のような意味を持つ名前
2. **使用意図の記述**: 「このトークンはどんな場面で使うか」の説明文
3. **トークン間の関係性**: 「エラー色を使う場合、テキストにはこのトークンも使うべき」という接続情報

Romina Kavcicの指摘: 「トークンはAIが必ず触れる唯一のレイヤー」（原文: "Tokens are the only layer AI always touches"）。トークンにセマンティックな意図を持たせることが、AI生成コードの一貫性を高める上で最も影響力の高い介入点になるという主張である。

### 11.2 フライホイール効果

強固なデザインシステム → より良いAI出力 → デザインシステムの強化 → より優れたコード生成

という好循環（フライホイール）が生まれる。

### 11.3 デザインシステムのAI対応チェック

- [ ] トークンにセマンティック名がついているか
- [ ] トークンに使用意図の説明文があるか
- [ ] コンポーネントにDoとDon'tが記述されているか
- [ ] トークン間の関係性が明示されているか
- [ ] MCPサーバー等でのプログラマティックアクセスが可能か

## 12. 各論者・組織の立場の比較と反対意見

### 12.1 主要な議論と反対意見

**「デザインシステムは必要か」という問い**:
- 小規模チーム（5人以下）では、デザインシステムのメンテナンスコストがその便益を上回る場合がある
- プロトタイプ段階のプロダクトでは、システム化が早すぎると柔軟性を損なう
- 反論: Atomic Designは思考モデルとしての価値があり、ツールや成果物がなくてもシステム的思考は有益

**「コンポーネントかトークンか」という議論**:
- 従来: コンポーネントがSSOT（Material UI等）
- 近年: トークンがSSOT、コンポーネントは派生物（Style Dictionary等）
- Brad Frost: 「コードが真実の源。Figmaはコードの現実を反映する鏡」

**「集中か分散か」という議論**:
- Nathan Curtisの分析: Federated Governanceは構造的に機能不全になりやすい——「フェデレーテッドの担当者は（追加の）システム作業を優先できない」と指摘し、80以上のデザインシステムのコンサルティング経験から中央専任チームなしに成功したシステムは「ゼロ」と述べている（特定の人数閾値ではなく構造上の問題として論じている）
- 解決策: 小さな専任コアチーム＋明確な貢献ルール

### 12.2 文脈依存性

デザインシステムの「正解」は組織規模、製品の多様性、チームの成熟度、ビジネス速度によって大きく異なる。以下は文脈依存の典型例:

| 文脈 | 推奨アプローチ |
|------|---------------|
| スタートアップ（1製品・小チーム） | 最低限のトークン＋スタイルガイド。本格的なシステムは後回し |
| 中規模企業（2〜5製品） | ハイブリッドガバナンス、コンポーネントライブラリ整備 |
| 大企業（多製品・多プラットフォーム） | 専任チーム、フルスタックシステム、貢献モデル確立 |
| マルチブランド | トークン階層を最大活用。ブランドごとのセマンティックトークンの差し替え |

## このリポジトリへの示唆

以下は、WhoOwnsDesignの文書設計に対してこの調査が示す含意である。

### 1. 「トークンを真実の源とし、コンポーネントは派生物」という構造を文書の骨格にする

デザインシステムの現代的な理解では、トークンが最も安定したSSOT。WhoOwnsDesignの文書設計も「プリミティブ→セマンティック→コンポーネント」の3層構造を軸に、各層の定義・命名規則・意図を記述する構造にすべき。

### 2. 「意図（Intent）」と「制約（Constraint）」を明示的に記録する形式を設計する

DEPT®の指摘通り、最重要な出力はデザインそのものでなくデザインインテントの橋渡し。各コンポーネント・トークン・パターンについて「なぜこれが存在するか」「どんな問題を解くか」「いつ使わないか」を記録する形式を設計に含める必要がある。

### 3. AIが消費できる形式を意識した記述規則を定める

FigmaのMCP ServerやAIエージェントは「トークン名の意味」と「使用意図の説明文」を頼りに判断する。WhoOwnsDesignがデザインシステム定義文書であるなら、その記述がAIによって解釈可能な形式（セマンティックな命名、Use/Don't Use記述、トークン間の関係性）であることを規則として定める必要がある。

### 4. 成熟度段階を明示し、「今どこにいるか」を文書に組み込む

Sparkboxモデルでは段階1〜4それぞれで優先すべき作業が異なる。WhoOwnsDesignの文書も「このフェーズで何を定義すべきか」という優先順位付けができるよう、成熟度を軸にした使い方ガイドを設けるべき。

### 5. 「使われないデザインシステム」の根本原因から逆算して文書を設計する

最大の失敗パターンは「誰も使わない」こと。WhoOwnsDesignが定義する文書群は、AIと人間の双方が「簡単に発見・理解・適用できる」設計である必要がある。ドキュメントの記述粒度・ナビゲーション・サンプルコードの充実が採用率を左右する。

### 6. 「原則」は他のすべての派生根拠となるため、最優先で定義する

NN/GとBrad Frostの両者が強調するように、原則（Principles）はコンポーネントよりも安定した基盤。WhoOwnsDesignの文書群では「なぜこのトークン体系か」「なぜこの命名規則か」を正当化する原則を最初に確立し、その後の決定を原則に紐付ける形式にすべき。

### 7. ガバナンスと更新プロセスを文書の一部として定義する

「誰がどう更新するか」が不明確なシステムは腐敗する。WhoOwnsDesignの文書定義においても、各文書種別の所有者・更新タイミング・変更提案プロセスを記述することで、文書群自体のライフサイクルを管理可能にする。
